# OpenAPI building blocks

This example API definition can be used to provide an OpenAPI 3.0, 3.1 or 3.2 definition for an implementation of _OGC API - Processes_, including
_Part 1: Core_, _Part 2: Deploy, Replace, Undeploy_, _Part 3: Workflows and Chaining_,
_Part 4: Job Management_ and _Part 5: Provenance_.
Paths of the parts that an implementation does not support can be removed from `ogcapi-processes.yaml`.
The API definition can be visualized with [SwaggerUI](https://petstore.swagger.io/?url=https://raw.githubusercontent.com/opengeospatial/ogcapi-processes/master/openapi/ogcapi-processes.bundled.json).

The lists of processes in the `/api` sub-directory should be tailored to the implementation & deployment, or those `/api/*` paths can be implemented dynamically by the server instead.
The list of supported paths should be ajusted in `ogcapi-processes-3.yaml`.

The `ogcapi-processes.bundled.json` was generated with `swagger-cli bundle` from `ogcapi-processes.yaml` and its dependencies included from the components sub-directories.

See also [SwaggerCLI](https://apitools.dev/swagger-cli/) and its [GitHub repository](https://github.com/APIDevTools/swagger-cli).

The `paths/processes-dru/pProcessListDeploy.yaml` and `paths/processes-dru/pProcessDescriptionReplaceUndeploy.yaml` files are generated by concatening multiple files in a single one.
You can run the [update.sh](update.sh) script use to both update them and execute `swagger-cli bundle`.

## OpenAPI versions

`ogcapi-processes.yaml` is the single editable source (declared as OpenAPI 3.0.3).
The per-version definitions `oas30-ogcapi-processes.yaml`, `oas31-ogcapi-processes.yaml` and `oas32-ogcapi-processes.yaml`
are generated by [update.sh](update.sh) and only differ by their `openapi` version.
They share the same components, which therefore must stay within the subset common to 3.0.3, 3.1 and 3.2:

- Use `oneOf` with `- enum: [null]` for nullable values (never `nullable`, nor `type: [X, "null"]`).
- Do not use `exclusiveMinimum`/`exclusiveMaximum` as keywords (boolean in 3.0, numeric in 3.1+).
- Do not use `const`, `$defs`, `$id`, `$schema`, `patternProperties` or tuple-style `items` in schemas.
- `format: binary` is kept (3.0 convention), with comments indicating the 3.1+ `contentMediaType`/`contentEncoding`.
- Remote `$ref` to non-OpenAPI JSON Schemas must not be used. Vendor an adapted copy instead (see `schemas/prov-json`).

Because _OGC API - Processes_ itself defines a `schema` field for the _ProcessDescription_ inputs and outputs,
its specific definition is a mixture of above components to allow any JSON schema variation.
For example, `exclusiveMinimum` is converted from plain `boolean` or `numeric` (according to respective JSON schema versions)
to a `oneOf: [boolean, numeric]` to accomodate any.
Similarly, nullable values can be represented by either `nullable: true`, `type: [X, "null"]` or `enum: [null]` in that field,
although only `enum: [null]` is allowed in all other definitions of this API. If this distinction is relevant in your _ProcessDescription_ definitions,
consider adding an explicit `$schema` property within the per-input/output `schema` contents to clarify which parser to employ.

## Validation

The check below bundles every variant, validates it against the official OpenAPI JSON Schema of its version,
verifies the rules above (`nullable`, component names), checks that the variants are in sync with the source,
and lints them with the Redocly configuration.
The same command is used locally and by the CI workflow ([openapi.yml](../.github/workflows/openapi.yml)).

```shell
cd openapi
npm install        # once (Node >= 22.12)
sh update.sh       # regenerate variants and bundle (BUNDLE_TOOL="npx --no-install redocly" to use the local install)
npm run validate   # or: node validate.mjs oas31
```
