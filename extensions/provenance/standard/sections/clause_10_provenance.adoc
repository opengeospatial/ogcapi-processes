[[clause_provenance]]
== Requirements Class "Provenance"

[[sc_provenance_overview]]
=== Overview

This requirements class defines how to allow client application accessing the provenance of a completed job resulting from
the execution of a process. Such process might be a predefined definition (<<OAProc-1,OGC API - Processes - Part 1: Core>>),
a mutable process (<<OAProc-2,OGC API - Processes - Part 2: Deploy, Replace, Undeploy>>), or a process that represents
a workflow (<<OAProc-3,OGC API - Processes - Part 3: Workflows and Chaining>>). The submitted job where provenance
details are collected from can result from a <<OAProc-1,OGC API - Processes - Part 1: Core>> process execution,
from <<OAProc-4,OGC API - Processes - Part 4: Job Management>> additional endpoints, or any other compatible extension.

For general information about provenance, see the <<W3C-PROV>> document.

[[sc_provenance_content]]
==== PROV Content

The server SHOULD provide structured PROV metadata elements that describe the executed process, job activity,
input/output entities, and useful associated metadata. Some definitions are required to ensure minimal interoperability
with guaranteed entities (e.g., Process and Job), while others are recommended guide server implementations toward
common practices. See also <<sc_prov-content-examples>> for concrete representations across various PROV formats.

[[sc_provenance_content-profiles]]
===== Profiles

When the <<rc_metadata-profiles,Metadata Profiles>> requirements class is supported, the profiles annotated
in the process description (see <<clause_metadata-profiles>>) can be carried over to the provenance of the job.
Profiles can also be reported without that requirements class, since a job can resolve profiles that are more
specific than the ones defined by the process (e.g., from the actual data or parameters submitted).
Such specialized profiles are strongly recommended, because they cannot be obtained otherwise.

[[sc_provenance_job-results-profiles]]
==== Job Results Profile

To ensure consistency between the <<OAProc-1>> job results and their provenance,
servers are encouraged to report the same profiles between them.

include::../recommendations/provenance/job-prov/REC_results-profile.adoc[]

NOTE: The `dataClasses` property of a by-value result can be located under a
link:++https://raw.githubusercontent.com/opengeospatial/ogcapi-processes/master/openapi/schemas/processes-core/qualifiedValue.yaml[qualifiedValue.yaml]++[`qualifiedValue.yaml`]
(i.e., at the same level as `value` and `mediaType`) within the representation of the job results response.
It is not available under other representations.

NOTE: The `profile` property of a by-reference result is employed instead of `dataClasses` for alignment with other
standards proposing this field. However, because the link is an open object as long as the `href` and `rel` are provided, servers
could also provide `dataClasses` or even the `headers` fields (replicating the above `Link` header) that are all allowed under the extended form of
link:++https://raw.githubusercontent.com/opengeospatial/ogcapi-processes/master/openapi/schemas/processes-core/link.yaml[link.yaml]++[`link.yaml`].
